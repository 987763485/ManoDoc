项目文档/产品简报/S1

DullDoc

本地优先的文档转换工作台

版本 v0.7 变更 S6 选型：Typst PDF · 不分发 pdf2docx 日期 2026-11-18 形态 Tauri 2 · macOS Apple Silicon 状态：已确认
一句话

把常见的可读文档转换成排版清晰、可直接使用的 Markdown，同时保留 Word、PDF、HTML、EPUB、图片等基础一对一互转；同一方向有多个引擎时可选择。需要时，再把一批文档洗成可入库的语料包。全程本地、离线、不联网。

不是又一个在线转换网站，也不是需要写脚本的 CLI 集合——是一个把「转 → 洗 → 切 → 打包」串起来的桌面工具。

01背景与痛点

文档转 Markdown 不是新需求，但今天的工具是离散的、常常联网的、并且默认牺牲排版。

工具离散 Word 用 Pandoc，PDF 用 Marker，Excel 靠脚本，Markdown 再导出又是另一套。每换一种格式就要换一个工具、记一套参数。
被迫联网 在线转换要先上传文件，涉及内部标准、测评报告、合同与制度时不可接受；网络抖动还会让批量任务中途失败。
排版丢失 标题层级塌陷、表格错列、中文断行错乱、页码与页眉混进正文——转出来的 Markdown「能看」，但没法直接用。
批量化门槛 要处理一个文件夹，就得自己拼命令、写循环、处理失败重试。非技术同事完全被挡在门外。

02目标用户

主要用户

需要长期、大量处理标准、报告、手册、制度文档的知识工作者——安全合规、研究、法务、咨询、技术写作。

典型动作：把 docx / PDF / xlsx 转成 Markdown，放入 Obsidian、语料库或喂给 LLM。

次要用户

团队里不写代码的同事。他们需要的是一个能拖拽、能看见进度、失败时知道为什么的 App，而不是命令行。

第一阶段不追求多人协作，但产物和参数必须可被同事复现。

明确不服务：需要精细排版出版的设计师、需要 PDF 逐像素精修的用户、需要在线协作与权限管理的团队。

03三个核心场景

Scene 01

单文件转换

拖入一个 docx / pdf / xlsx，自动识别格式并转换；左侧看渲染效果、右侧看 Markdown 源码；确认后保存，或用 pandoc 导出 HTML / DOCX / EPUB。

Scene 02

批量转换

拖入一个文件夹，递归扫描；任务队列显示每个文件的进度、引擎、耗时与警告；失败可单独重试；输出保持原目录结构。

Scene 03

语料包

批量转换时勾选清洗、切块、元数据，输出镜像 .md + chunks.jsonl + manifest.json，直接交给任意 RAG / 向量库流程。

04产品原则

1
本地优先，默认离线转换、清洗、切块全部在本机完成；不登录、不上传、不埋点。联网能力只作为未来可选扩展。
2
保真优先于速度标题层级、表格、列表、公式、图片位置必须尽量保留；宁可慢一点，也不要产出「看起来对、实则错位」的 Markdown。
3
一站式，不拼命令格式识别、引擎选择、参数、输出组织都在界面里完成；高级用户仍可查看和复用实际参数。
4
可解释、可定位每个文件都能看到用了哪个引擎、哪些步骤被跳过、为什么失败；错误信息给原因和下一步，而不是一个红色感叹号。
5
可复现预设、参数、引擎版本与输入哈希写入 manifest；同样的输入与预设，产出同样的语料包。

05MVP 范围

P0 = MVP 必须；P1 = 紧随其后；P2 = 暂不规划。详细拆解与 REQ 编号在 S4 完成。

模块能力说明优先级
单文件格式识别 + 转换 + 保存 anydoc 负责 docx / pdf / xlsx / pptx / odt / rtf / epub / csv；支持拖拽与文件选择；转换进度与错误在配置卡内联显示，不提供文档预览。 P0
多方向转换基础一对一文档互转 Word ↔ Markdown、PDF → Markdown / Word、Markdown → Word / PDF / HTML / EPUB、PNG/JPEG → Markdown、Excel/CSV 与 PowerPoint → Markdown；PDF→Word 与 Markdown→PDF 标注质量/渲染器限制。 P0
引擎选择自动 + 显式引擎 同一方向有多个引擎时列出兼容引擎；自动按格式、质量与可用性路由，显式选择优先并写入 manifest。 P0
文件图标文件类型标记 转换页、批量、历史与方向矩阵使用统一图标；缺失时回退通用文档图标。 P0
第二内核xberg 引擎 扫描件 / 图片 PDF、复杂表格、anydoc 失败回退；Rust + MIT；S6 验证体积与稳定性。 P0
导出Markdown → HTML / DOCX / EPUB 由 pandoc sidecar 执行；输出前可调模板与选项。 P0
批量文件夹递归 + 队列 + 进度 + 取消 + 重试 镜像原目录；并发可配置；失败明细可导出。 P0
清洗页眉页脚 / 页码 / 水印 / 断行 / 空段 / 标题规范 逐项可勾选，默认保守；每次改动可在输出与警告中核对。 P0
切块按标题切分 + 表格整块 + 超长二次切分 字符 / token 上限与重叠可配置；保留章节路径。 P0
语料包chunks.jsonl + manifest.json 厂商中立字段：id、text、source、title、headings、page、hash 等；完成行可打开输出文件或目录。 P0
基础体验设置、日志、错误处理、任务历史 全局日志与错误归因；敏感信息不落盘。 P0
体验中英文 / 主题 / 命令面板 中文默认、英文完整；跟随系统/浅色/深色；Cmd+K 搜索与执行。 P0
Python 运行时uv + 隔离 .venv 内置 uv；在 ~/.dull_doc/runtimes/<engine>/.venv 按需安装；不依赖系统 Python，不静默下载。 P1
扫描件备选Marker 引擎接入 Marker 作为 P1 的高质量备选；MVP 的扫描件由 xberg 覆盖；通过 uv 托管运行时。 P1
OCR 增强PaddleOCR（P1） 中文 OCR / PP-Structure；通过 uv 隔离 .venv 按需安装；xberg 低置信度或用户选择时启用。 P1
PDF 输出Markdown → PDF pandoc 生成 Typst，再由 Typst sidecar 编译 PDF；中文字体优先系统字体，必要时 bundle Noto CJK；缺失时阻止并提示。 P0
自动化文件夹监听、预设、命令行入口 面向高频重复任务。 P1
跨平台Windows / Linux macOS 验证稳定后再扩展。 P2

06MVP 明确不做

  • 账号体系、云同步、云端转换与在线 OCR
  • 团队协作、权限、评论与版本对比
  • 向量库管理、检索问答界面
  • PDF 精修、复杂排版出版、公式所见即所得编辑
  • 插件市场与第三方脚本运行时
边界：MVP 的目标不是覆盖所有格式，而是把「常见可读文档 → 可直接使用的 Markdown」这条路做到稳定、可解释、可批量。

  • 批量 50 个文件不崩溃；任一失败都能在界面上定位到文件与原因
  • 断网状态下完成单文件、批量、语料包全流程

  • 日常 80% 的转换不再需要打开终端或浏览器

08关键假设与风险

项假设 / 风险应对
anydoc 表格能力 中文标准文档的合并单元格、跨页表格可能被简化或错位。 S2 用 example 真实样本验证；必要时增加表格后处理规则。
pandoc 分发 pandoc 为 GPL 程序，sidecar 分发需合规处理。 独立进程调用，附许可证与源码获取说明；不静态链接。
xberg 体积 / 稳定性 OCR 与版面模型可能增加依赖、安装体积与平台差异。 S6 用真实样本验证；若不可行则降级 P1，回退到 anydoc + 跳过策略。
PaddleOCR 依赖 Python + Paddle 模型，macOS 上以 CPU 为主；体积与速度需评估。 P1 可选组件，引导安装；不进入 MVP 默认路径。
Marker 体量 Python + 模型数 GB，不适合塞进 MVP 安装包。 P1 采用「检测环境 + 引导安装」或本地服务方式。
PDF 输出 PDF 输出需 Typst sidecar 与中文字体；LaTeX 体积大且本机缺失。 MVP 采用 pandoc → Typst；不使用 LaTeX；spike 验证分页、字体与表格。
“可读文档”边界 加密文件、扫描件、损坏文件、超长文档会打破「一键成功」的预期。 按错误类型给出明确提示与下一步，不做静默失败。

09已确认决策

以下决策已于 2026-11-18 确认，将写入 S3 需求文档。

议题建议理由备选
产品名 保留 DullDoc 与仓库、文档路径和 Bundle ID 一致；「Dull in, clean out」本身就是清晰的品牌叙事；MVP 阶段改名会牵动安装包、签名与全部文档。 面向大众品牌时再评估 TidyMark / MarkCraft。
图片 默认落 assets/ 相对路径；单文件导出可选内嵌 base64 Markdown 保持可读、可 diff、不撑爆 LLM 上下文；批量语料、Obsidian 与静态站点都依赖独立资源目录。 base64 仅用于「便携单文件」场景，不作为默认。
历史 保留最近 50 条任务元数据（可配置） 支持回看、重跑、失败定位与参数对比；只存路径、参数、哈希与结果摘要，不复制文件，存储成本很低。 不做历史：实现更简单，但批量失败时难以复盘。
新增内核 xberg（P0 第二内核） Rust + MIT，负责扫描件 / 图片 PDF 的 OCR、复杂表格与 anydoc 失败回退；Marker 保留 P1。 S6 验证不达标时降级 P1，需用户确认。
OCR 增强 PaddleOCR（P1） Apache-2.0，中文 OCR 强；作为 xberg 低置信度时的可选组件，不随包分发模型。 若 macOS 依赖过重，保留为可安装组件，不影响 MVP。
体验 中英文 + 主题 + 命令面板（P0） 中文默认、英文完整；跟随系统/浅色/深色；Cmd+K 键盘优先。 文案与主题 token 在 S5 设计规范中定义。
开源协议 MIT 与 anydoc 一致，个人与小团队采用门槛最低；pandoc 作为独立 sidecar 按 GPL 合规分发，并在「关于」页给出源码获取方式。 Apache-2.0：需要专利授权或企业法务友好时切换。
已确认的组合：DullDoc · 图片落 assets/ · 保留 50 条元数据 · MIT · xberg P0 · PaddleOCR P1。前四项在 S1 确认；xberg 与 PaddleOCR 为 2026-11-18 追加决策，可在 S3 定稿前调整。
