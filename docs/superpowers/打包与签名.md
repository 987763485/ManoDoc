# DullDoc 打包与签名（macOS Apple Silicon）

> 对应 CHG-005 `packaging-signing`。本文件记录打包命令、sidecar 分发方式、签名链、验证结果与公证阻塞。
> 技术背景见 `docs/superpowers/技术选型.md`；发布前需要补齐 Developer ID 后才能对外分发。

## 一、打包入口

```bash
pnpm package:mac
```

脚本 `scripts/package-macos.sh` 依次执行：

1. 校验主机为 arm64；
2. 从 `tools/macos/` 复制 pandoc、Typst、uv 到 `src-tauri/binaries/<name>-aarch64-apple-darwin`（该目录不入库）；
3. 逐个对 sidecar 签名（默认 ad-hoc，`codesign --sign -`）；
4. 设置 `TESSERACT_RS_CACHE_DIR` 与 `APPLE_SIGNING_IDENTITY` 后执行 `pnpm tauri build --target aarch64-apple-darwin --bundles app,dmg`；
5. 校验 `.app` 的 sidecar、签名、Info.plist；
6. 挂载 `.dmg`，确认卷内含 `DullDoc.app`；
7. 执行 `spctl` 评估并输出签名与 Gatekeeper 结果；
8. 无 Developer ID 时输出公证剩余步骤，并以退出码 `20` 结束。

退出码：`0` 表示打包并完成公证；`20` 表示打包成功、等待 Developer ID 公证；其他为打包失败。

## 二、sidecar 分发与解析

- `src-tauri/tauri.conf.json` 的 `bundle.externalBin` 声明 `binaries/pandoc`、`binaries/typst`、`binaries/uv`。
- 打包后位于 `DullDoc.app/Contents/MacOS/`，与主程序同目录，Tauri 会去掉 target triple 后缀。
- 运行时解析顺序（`src-tauri/src/engine/sidecar.rs`）：
  1. 环境变量 `DULLDOC_PANDOC` / `DULLDOC_TYPST`；
  2. 应用同目录（打包形态命中这里）；
  3. 项目内 `tools/macos/*`（仅开发期）。
- 全部缺失时返回 `E_PANDOC_MISSING` / `E_TYPST_MISSING`，错误详情列出已检查路径，不回退系统 `pandoc`。
- uv 当前无调用方，按已确认的 P1 决策随包预留，不启用任何安装逻辑。

## 三、签名链

顺序自内向外：sidecar → `.app` 外层。

- 无 Developer ID：全部使用 ad-hoc。Tauri 只有在显式收到 `APPLE_SIGNING_IDENTITY="-"` 时才会生成 `_CodeSignature/CodeResources`；不设置时只留下 linker 签名，`codesign --verify --deep --strict` 会报 “code has no resources but signature indicates they must be present”。
- 有 Developer ID：`export DULLDOC_SIGN_IDENTITY="Developer ID Application: <团队名> (<TEAMID>)"` 后重跑脚本，sidecar 使用 hardened runtime 与时间戳，`.app` 由 Tauri 用同一身份签名，随后脚本执行公证与 staple。

## 四、产物

| 产物 | 路径 | 大小 |
| --- | --- | --- |
| 应用 | `src-tauri/target/aarch64-apple-darwin/release/bundle/macos/DullDoc.app` | 约 380 MB |
| 安装镜像 | `src-tauri/target/aarch64-apple-darwin/release/bundle/dmg/DullDoc_0.1.0_aarch64.dmg` | 约 128 MB |

`Contents/MacOS/`：`dulldoc`、`pandoc`、`typst`、`uv`。

### 前端资源策略

前端由 Tauri 内嵌进主可执行文件，`Contents/Resources/` 只有 `icon.icns`。这是 Tauri 2 的默认加载方式：启动更快、无路径解析与权限问题，前端字节同样受签名封条保护。

由此产生的验收口径：

- 不要求 `Resources` 出现 `index.html` 或 `assets/`；出现即视为重复打包，检查失败。
- 打包脚本会拒绝 `Resources` 中大于 10 MB 的未声明文件，防止资产误放导致体积失控。
- 需要人工审计或热替换前端时才考虑外置方案（`bundle.resources` + 自定义协议），普通分发不采用。
Info.plist：版本 `0.1.0`、标识 `dev.dulldoc.app`、最低系统 `12.0`、图标为生成的 `icon.icns`。

## 五、验证结果（2026-11-19）

- `pnpm package:mac`：打包成功，退出码 `20`（待公证）。
- `codesign --verify --deep --strict`：通过；`codesign -dv` 显示 `Signature=adhoc`，`Sealed Resources version=2`。
- DMG：挂载卷 `DullDoc`，内含 `DullDoc.app`；从挂载卷复制出的应用签名校验通过并可启动。
- 打包应用实机（隐藏 `tools/macos` 下的 pandoc/typst 后启动）：
  - Markdown → Word：25,071 字符、212 标题、121 表格行，引擎 `pandoc`；
  - Markdown → PDF：21 页、672 KB，引擎 `pandoc + typst`，文件以 `%PDF-1.7` 开头。
  以上证明转换使用包内 sidecar，而非开发目录。
- 缺 sidecar：从副本移除 `Contents/MacOS/pandoc` 并重签后启动，转换返回 `E_PANDOC_MISSING`，详情列出 `Contents/MacOS/pandoc` 等已检查路径。
- `spctl --assess`：`rejected`（无 Developer ID 时的预期结果）。
- `pnpm build`、`pnpm test`（13 项）、`cargo check`、`cargo test`（25 项 + 12 ignored）通过。

## 六、公证阻塞与发布前 checklist

本机 `security find-identity -v -p codesigning` 为 0 个有效身份，无法执行公证。发布前需要：

1. 申请并安装 **Developer ID Application** 证书；
2. `export DULLDOC_SIGN_IDENTITY="Developer ID Application: <团队名> (<TEAMID>)"` 后重跑 `pnpm package:mac`；
3. 保存公证凭据：`xcrun notarytool store-credentials dulldoc-notary --apple-id <AppleID> --team-id <TEAMID> --password <app-specific-password>`；
4. 脚本自动分别公证 `.app` 与 `.dmg`（`xcrun notarytool submit ... --wait`）；
5. 公证成功后 `xcrun stapler staple` 并再次 `spctl --assess` 复核；
6. 首次对外分发前，在干净机器上（无本地构建记录）下载安装验证一次 Gatekeeper 流程。
