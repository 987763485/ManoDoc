竞品分析

文档互转与 Markdown 工作台：功能面、实现原理与 ManoDoc 的机会

版本 v0.7 变更 S6 选型：Typst PDF · 许可收敛 日期 2026-11-18 样本 40+ 产品与项目 · 61 项功能面 状态：已确认

00结论摘要

FINDING 01 没有产品同时满足「本地离线 + 多格式 + 中文清洗 + 批量语料包 + 可解释」

商业套件强在 OCR 与 PDF 编辑，但在线或昂贵、不产 Markdown；开源引擎强在解析，但要么缺 OCR，要么缺批量与清洗，要么需要写代码。

FINDING 02 anydoc 是 Office 与文本型 PDF 的最佳起点，但 PDF 是「全有或全无」

任一页没有文本层，整份 PDF 直接失败。真实样本的封面页就让 50 页文档无法转换；移除封面后，标题与表格立即恢复。

FINDING 03 pandoc 是导出器，不是抽取器

docx 没有 Heading 样式时，pandoc 输出 0 个标题；anydoc 通过字号/加粗/编号识别出 49 个。pandoc 的价值在 Markdown → HTML/DOCX/EPUB。

FINDING 04 真实样本证明「清洗层」是刚需

中文标准文档普遍存在字间空格、标题编号断行、目录点线、表格内换行。原样输出「能看」，但达不到「排版清晰、可直接使用」。

FINDING 05 xberg（原 Kreuzberg）是最接近的潜在竞品，并已被选为第二内核

Rust、MIT、107 种格式、Markdown/OCR/表格/切块/CLI/API/MCP。它证明「Rust 文档智能 + 语料化」这条路成立；2026-11-18 用户决定将其纳入 ManoDoc 内核，作为 P0 第二引擎，S6 负责落地验证。

FINDING 06 ManoDoc 的机会在「最后一公里」

不是再造一个解析引擎，而是把引擎路由、PDF 预检、中文清洗、质量诊断、批量队列与语料包组合成一个离线桌面工作台。

01方法与范围

S2 的目标不是罗列所有软件，而是建立一张足够完整的功能面地图，找出 ManoDoc 必须做、可以做和不该做的位置。

竞品分层

  • 商业桌面 PDF 套件：Acrobat、ABBYY、PDFelement、Nitro、Foxit。强在 OCR、PDF 编辑、Office 导出。
  • 在线转换服务：Smallpdf、iLovePDF、CloudConvert、Convertio、Zamzar。强在触达与格式数量，弱在隐私与离线。
  • 专业文档解析 / SDK：Mathpix、Datalab Marker、Aspose/GroupDocs、Apryse、Docparser。强在精度与可集成，弱在价格与上手成本。
  • 开源解析引擎：Pandoc、anydoc、Marker、MinerU、Docling、MarkItDown、xberg、Unstructured。强在可控与可组合，弱在工程封装。
  • 相邻平台：Stirling PDF、Paperless-ngx、RAGFlow、Obsidian Importer、PanWriter、LibreOffice、Calibre。提供能力拼图，但不是端到端产品。

评价维度

  • 输入覆盖：Office、PDF、扫描件、图片、网页、邮件、音视频。
  • 解析保真：标题、列表、表格、合并单元格、公式、图片、阅读顺序、页眉页脚。
  • 输出与语料化：Markdown / HTML / DOCX / PDF / JSON；清洗、切块、元数据、manifest。
  • 工作流：单文件、批量、队列、重试、监听、CLI/API、预设、历史。
  • 部署与合规：离线、macOS/Windows/Linux、开源许可、隐私、价格。
数据来源与边界：官网功能页、GitHub 仓库（星标与许可证截至 2026-11-18）、公开评测，以及本机对 `example/` 四份测试文件的真实转换。厂商自测（如 anydoc 的 4.4ms/81 分）只作为线索，不作为结论；价格与免费额度随时变化，以官网为准。功能矩阵中的「△」表示部分支持、需付费、需额外依赖或存在明显限制。

02市场全景

把「文档 → Markdown」拆成五层能力后，竞争空白非常清楚：越靠近「解析」，开源越强；越靠近「工作流与语料化」，产品越少；同时做到离线、批量、清洗、可解释的桌面产品，几乎没有。

层级代表产品核心能力对 ManoDoc 的意义
商业 PDF 套件 Acrobat Pro、ABBYY FineReader、PDFelement、Nitro、Foxit OCR、PDF 编辑、Office 导出、批处理、电子签名、合规 证明用户愿意为「准确 + 省事」付费；但都不产 Markdown，且重、贵、偏 PDF 编辑。
在线转换服务 Smallpdf、iLovePDF、CloudConvert、Convertio、Zamzar 格式多、即开即用、API、云端批处理 证明「转换」是高频需求；但上传文件、依赖网络，不适合内部标准与测评资料。
专业解析 / SDK Mathpix、Datalab Marker、Aspose/GroupDocs、Apryse、Docparser 公式/表格/版面高精度、API、私有化 证明高质量解析有溢价；但面向开发者与大型客户，普通知识工作者用不上。
开源解析引擎 Pandoc、anydoc、Marker、MinerU、Docling、MarkItDown、xberg、Unstructured 格式覆盖、OCR、表格、公式、Markdown、切块 ManoDoc 的引擎池；需要封装、路由、清洗与 UI，才能变成产品。
相邻平台 Stirling PDF、Paperless-ngx、RAGFlow、Obsidian Importer、PanWriter、LibreOffice、Calibre PDF 工具、文档管理、RAG 解析、笔记导入、排版转换 说明「文档入口」与「语料出口」都有需求，但没人把中间那段做成顺滑的本地工作台。
竞争空白：「离线可用的中文文档 → 干净 Markdown → 可入库语料包」这一段，商业产品不做，开源引擎不封装，在线服务不敢离线。ManoDoc 不需要赢过 Marker 的 OCR，只需要把 80% 的常见文档稳定地送到「可直接使用」的状态。

5.4 结论：ManoDoc 的组合机会

单个维度上，ManoDoc 都很难赢：OCR 赢不过 ABBYY/Marker，格式数量赢不过 CloudConvert/xberg，RAG 切块赢不过 RAGFlow/Unstructured。
但组合起来，空白非常明确：macOS 原生、完全离线、中文优先、anydoc 快速解析 + xberg OCR/表格增强 + pandoc 导出、PDF 页级预检、清洗/切块/语料包、批量队列与可解释诊断——目前没有产品同时做到。
后续决策（2026-11-18）：用户决定将 xberg 纳入 ManoDoc 内核，作为第二解析引擎，负责扫描件/图片 PDF 的 OCR、复杂表格与 anydoc 失败回退；同时将 PaddleOCR 纳入 P1，作为中文 OCR 增强组件。同日增补中英文切换、跟随系统/浅色/深色主题与 Cmd+K 命令面板。

范围再扩展（2026-11-18 优化请求）：保留基础一对一互转（Word ↔ Markdown、PDF → Markdown / Word、Markdown → Word / PDF / HTML / EPUB、PNG/JPEG → Markdown 等），同一方向多引擎时提供引擎选择；Python 引擎由内置 uv 在应用数据目录创建隔离 `.venv`；文件类型统一使用图标。竞品中「格式互转」已是基础能力，ManoDoc 的差异仍在离线、可解释的多引擎编排与语料化；实施要求见 PRD REQ-106 ~ REQ-110。

06实现技术与原理

文档转换不是「读文件、写字符串」，而是三种完全不同的技术路线在同一个产品里协作。理解它们的边界，才能设计正确的引擎路由。

6.1 三条解析路线

路线原理代表优点局限
结构化解析 解压 OOXML/ODF 容器，解析 XML（段落、样式、表格、关系、嵌入资源），建立统一文档模型后序列化为 Markdown。 anydoc、Mammoth、Pandoc、xberg（文档部分） 快、确定、无需模型；标题/列表/表格/公式结构准确。 依赖源文件结构；无样式标题可能识别失败；扫描件无能为力。
版式 / 视觉解析 把 PDF/图片渲染为页面，做版面检测（标题/正文/表格/图/页眉页脚）、OCR、阅读顺序重建、表格结构识别、公式识别，再生成 Markdown。 Marker/Surya、MinerU、Docling、RAGFlow DeepDoc、Mathpix 能处理扫描件、复杂版式、多栏、表格与公式。 模型体积大、速度慢、资源占用高；结果有概率性，需要置信度与人工复核。
规则 / 工具封装 调用 LibreOffice、Pandoc、Tika、Calibre 等外部程序，或按固定规则做文本/表格抽取。 CloudConvert、Stirling PDF、LibreOffice、Pandoc 格式覆盖广、实现成本低、生态成熟。 Markdown 结构弱；排版保真取决于工具；难以做中文清洗与语料化。

6.3 anydoc 的关键设计

  • 共享文档模型：每种格式先解析成同一套块模型（标题、段落、列表、表格、图片、脚注），再由单一 Markdown 序列化器输出。这保证跨格式的转义、表格、锚点行为一致。
  • 内容级识别：读 PDF 头、RTF 开组、OLE 流名、ZIP mimetype，而不是只看扩展名。
  • 无 OCR：文本型 PDF 通过 pdf-inspector 提取；任一页需要 OCR 时返回 NeedsOcr，CLI 退出码 3。
  • 公式：OMML/MathML → LaTeX；图片保留原始字节，Markdown 中以 alt 文本占位。

6.4 pandoc 的关键设计

  • AST 中间表示：reader 把输入解析为 Pandoc AST，writer 再生成目标格式；过滤器可在 AST 上做变换。
  • 模板系统：HTML/DOCX/LaTeX 输出都可通过模板控制样式。
  • PDF 依赖外部引擎：默认 pdfLaTeX；也可用 XeLaTeX、LuaLaTeX、Typst、wkhtmltopdf、WeasyPrint 等。
  • 不是抽取器：docx 标题依赖 Word 的 Heading 样式；没有样式时，pandoc 不会猜测。

6.5 版面 / OCR 引擎的关键设计

环节常见做法代表实现
版面检测目标检测模型识别标题、正文、表格、图片、页眉页脚等区域；再按坐标与阅读顺序排序。Docling RT-DETR/Heron、Marker Surya、MinerU layout、RAGFlow YOLOv10
OCR文本检测 + 识别；中文常用 PP-OCR、Surya、Tesseract；VLM 路线直接用多模态模型读图。PaddleOCR、Surya、Tesseract、MinerU VLM
表格结构识别行/列/表头/合并单元格；输出 HTML 表格或结构化单元格网格。TableFormer（Docling）、TATR/SLANet（xberg）、Marker TableConverter、MinerU 跨页表格
公式检测公式区域 → 识别为 LaTeX；行内公式需要与正文对齐。Mathpix、Marker、MinerU、UniMERNet
阅读顺序基于坐标、栏检测与相邻块关系，重建单栏/多栏阅读顺序。RAGFlow XGBoost、Docling reading order、Marker

6.6 语料化：从 Markdown 到可入库数据

  • 切块：优先按标题层级切（H1/H2/H3），表格作为整块保留；超长块再按字符/token 上限二次切分，并保留重叠。
  • 元数据：来源路径、文件名、格式、标题、章节路径、页码、输入 hash、引擎与参数、字符/token 数。
  • manifest：记录每个文件的输入、输出、状态、耗时、警告与引擎版本；保证同输入 + 同预设可复现。
  • 厂商中立：chunks.jsonl 每行一个 {id, text, metadata}，不绑定 Dify/RAGFlow；需要时再由适配器转换。

7.3 五个结论

01 anydoc 的 docx 结构识别明显优于 pandoc

49 vs 0 的标题差距，来自 anydoc 对字号、加粗、编号的综合判断。对没有 Heading 样式的中文标准文档，这是决定性优势。

02 PDF 必须有页级预检

一个纯图片封面就让整份文档失败。MVP 必须逐页检测文本层，提供「跳过无文本页」并记录警告；否则用户会觉得「工具坏了」。

03 复杂 PDF 表格不是 MVP 能承诺的

去封面后虽然能输出 204 行表格，但多段文字被塞进同一单元格。若承诺「排版清晰」，需要 P1 的版面/OCR 引擎，或明确的「表格质量警告」。

04 清洗层决定「可用」与「能看」

字间空格、标题编号、目录点线、页眉页脚，都是规则可解的。它们不性感，但正是 ManoDoc 相对原始引擎的核心价值。

05 xlsx 是意外的高分项

1048 行表格直接可用，说明「表格型标准/清单」是 ManoDoc 可以立刻交付价值的场景，甚至可以先于 PDF 做深。

06 pandoc 的定位应收缩到「导出」

不要用它做 docx 抽取；用它做 Markdown → HTML/DOCX/EPUB/Typst。PDF 已选 Typst 编译，不使用 LaTeX。

厂商基准提醒：anydoc 官方 benchmark 宣称 14/14 格式、4.4ms 中位耗时、81 分质量，但这些数据来自厂商自建语料与 LLM 评判，不是独立评测。上面的真实样本结果，才是 ManoDoc 做决策时更可靠的依据。

08功能机会与建议

基于竞品空白与真实样本，以下 12 项是「值得加、且竞品没有同时做好」的功能建议。它们会在 S3 转成需求编号，在 S4 排入 MVP。

#建议功能解决什么问题竞品空白优先级
01PDF 页级预检与「跳过无文本页」封面/插图页导致整份 PDF 失败anydoc 全有或全无；商业套件不暴露页级诊断P0
02中文排版清洗规则集字间空格、标题编号、目录点线、全半角开源引擎只做结构，不做中文规范化P0
03表格保护与质量分级合并单元格、跨页表格、复杂单元格anydoc 尽力而为；商业套件不产 MarkdownP0
04质量诊断与内联错误用户不知道哪里转坏了开源 CLI 只给退出码；商业 GUI 不解释结构P0
05批量队列：并发、取消、重试、跳过已存在文件夹转换不可控开源引擎缺 GUI；在线服务不适合内部资料P0
06语料包：chunks.jsonl + manifest转完还要写脚本切块与加元数据RAGFlow/Unstructured 重且平台化；桌面产品缺失P0
07预设与可复现每次参数不同，结果不可比多数工具只记全局设置，不记引擎版本与哈希P0
08xberg 第二内核（OCR / 复杂表格）扫描件、复杂 PDF 表格、anydoc 失败回退Marker/MinerU 强但重；xberg 为 Rust + MIT，可作为 P0 增强P0
09引擎插件化今天是 anydoc，明天可能是 xberg/MinerU没有产品把多引擎做成可解释的路由层P1
10监听文件夹 + CLI + Finder 快捷操作固定投递目录与自动化商业套件有但重；开源引擎只有 CLIP1
11中文标准文档专项红头文件、印章、条款编号、竖排通用工具不处理中国公文/标准格式P1
12集成导出（Obsidian / Dify / RAGFlow / Webhook）转完还要手工搬运平台各自为政；ManoDoc 可做中立出口P2
13PaddleOCR 中文 OCR 增强中文扫描件、低置信度 OCRxberg 内置 OCR 可选 PaddleOCR 后端；独立组件更可控P1
14中英文切换 / 主题 / 命令面板双语用户、长时间使用、键盘操作商业套件有中英文与主题，但命令面板通常只有开发者工具具备P0

不建议做

  • PDF 编辑、注释、表单、电子签名——这是 Acrobat/ABBYY 的战场。
  • 在线转换站、云账号、团队协作——与「本地、离线、隐私」定位冲突。
  • 向量库管理、检索问答 UI——ManoDoc 只负责把语料做好，不负责消费语料。
  • 追求 1100+ 长尾格式——主流 8 类格式做深，比格式数量更有价值。
  • 自研 OCR / 版面模型——接入成熟引擎，专注清洗、路由与体验。

09风险与待决

风险 / 待决影响建议
anydoc 对 PDF 的页级失败 含封面、插图、扫描页的 PDF 直接不可用；真实样本已复现。 P0 做页级预检 + xberg OCR 回退；xberg 不可用时才跳过 / 失败。
复杂 PDF 表格保真 「排版清晰」的承诺在复杂表格上不成立。 P0 做质量分级 + xberg 回退；Marker / MinerU 作为 P1 备选。
中文清洗规则误伤 过度去空格可能破坏英文、代码、URL、化学式。 规则分域：CJK 之间去空格；CJK 与 Latin 之间保留；代码/公式块跳过；提供规则开关与输出核对。
Marker / MinerU 的模型许可 代码开源，但模型权重有商用门槛或附加条件。 S6 逐项核对许可；默认「检测环境 + 用户自装」，不随安装包分发模型。
pandoc GPL 分发 sidecar 分发需合规。 独立进程调用，附许可证与源码获取方式，不静态链接。
PDF 输出 LaTeX 体积大、安装复杂；本机已验证缺失 pdflatex 即失败。 MVP 用 pandoc → Typst；不引入 LaTeX；Typst sidecar 需签名与字体验证。
xberg 的稳定性与模型依赖 项目刚更名，OCR/表格模型可能带来体积、平台差异与许可问题。 已定为 P0 第二引擎；S6 用真实样本验证体积、速度与许可，不达标再降级 P1。
PaddleOCR 依赖 Python + Paddle 模型，macOS 上以 CPU 为主；体积与速度需评估。 P1 可选组件，引导安装；不进入 MVP 默认路径。
macOS 签名 / 公证 含 sidecar 与可选 Python 环境，分发复杂。 MVP 先做本地开发版；P1 处理 Hardened Runtime、entitlements、notarization。
